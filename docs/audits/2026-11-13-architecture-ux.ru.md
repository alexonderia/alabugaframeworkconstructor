## Вывод

Основной пользовательский цикл работает: создание проекта → редактирование → сохранение → предпросмотр → экспорт. Живая генерация одной секции через Qwen3.5-2B и применение черновика прошли успешно. Самостоятельный HTML открылся с заблокированными HTTP(S)-запросами.

Приоритетные изменения: устранить неоднозначность заголовков презентации; разделить обязанности крупных модулей редактора; упростить настройки и завершение ИИ-сценария; обновить сведения о версиях в документации. Переписывать весь продукт или переносить проекты на сервер оснований по этому аудиту нет.

`P1` — следующая итерация: существенное затруднение основной задачи или сопровождения. `P2` — плановая доработка. `P3` — улучшение удобства. Приоритеты отражают оценку воздействия; это не результаты исследования с пользователями.

## Фактическая архитектура

| Слой | Где находится | Ответственность |
| --- | --- | --- |
| Библиотека Framework | Внешний точный npm-пакет `@alabuga/framework@1.3.1` | Схема, компоненты, renderer, композиции, standalone runtime, экспорт |
| Редактор | `apps/editor` | Галерея, hash-маршруты, модель редактирования, холст, инспектор, локальные проекты, UX ИИ |
| Генерация ИИ | `packages/ai` | Контракты, провайдер, планирование, команды, проверка содержания |
| HTTP-сервис | `apps/ai-server` | Прокси к Ollama, лимиты, readiness, bootstrap; также умеет раздавать статические файлы при запуске без nginx |
| Хранение проектов | IndexedDB браузера | Проекты, summaries, изображения, история, настройки; база версии 3 |
| Web runtime | nginx → API → Ollama | Статика и `/api/ai/`; проекты на сервер не отправляются |
| Сборка и интеграция | Корневые `scripts`, npm workspaces, CI | Сборка editor/AI/server, документация, контрактные проверки, Docker |

Предпросмотр и preflight создают iframe с тем же standalone runtime, который используется для HTML-экспорта. ИИ готовит отдельный черновик и применяет его после проверки. Разделение репозиториев Framework и Constructor уже реализовано.

Сильные решения, которые стоит сохранить:

- Оптимистическая версия проекта проверяется внутри транзакции IndexedDB; BroadcastChannel служит уведомлением, а не единственной защитой от перезаписи.
- Очередь сохранения объединяет ожидающие снимки, не подтверждает старую запись как последнюю; выход из редактора ожидает сохранения.
- Изображения дедуплицируются; очистка проверяет ссылки проектов, истории, корзины и черновика в транзакции.
- Ограничены история undo, кэш материалов и число одновременно работающих рендереров миниатюр.
- Есть обработка фокуса, модальных окон, мобильных панелей, ошибок сохранения и восстановления.
- В графе статических относительных TypeScript-импортов 71 исходного файла editor/demo/AI/server циклы не обнаружены. Динамические импорты и все возможные runtime-зависимости этим анализом не покрывались.

## Архитектура и файловая организация: что изменить

### A1 · P1 · Разделить управление сессией редактора и построение интерфейса

[main.ts](../../apps/editor/src/main.ts), начиная с `mountEditor` на строке 40, объединяет выбор элементов, команды, DOM, инспектор, историю, конфликты, сохранение, preview/export, обработчики и завершение сессии. Файл содержит 37 импортов, около 42 КБ UTF-8. Объём скрывается за 273 очень плотными строками.

Это увеличивает число состояний, которые приходится учитывать при обычной правке интерфейса. Рекомендация: оставить `mountEditor` точкой сборки; выделить состояние и жизненный цикл сессии, команды документа, контроллер холста, координацию инспектора и сохранение. Существующие `EditorModel` и `EditorSaveQueue` — подходящие опоры. Изменять одну ответственность за PR с существующими тестами переходов, конфликтов и сохранения.

### A2 · P2 · Восстановить читаемый исходный код и ясные имена файлов

[app.ts](../../apps/editor/src/app.ts) содержит строку длиннее 4400 символов; в `main.ts`, `design.ts`, `properties.ts`, `storage.ts` встречаются строки порядка 1000 символов. Это исходники, а не результат сборки. В `package.json` нет команды форматирования или обычного линтинга TypeScript.

Сначала нужен отдельный PR только с форматированием и проверкой формата в CI. Затем — осмысленные модули по функциям. Названия `style.css`, `styles.css`, `product.css`, `workspace.css` не объясняют, какой слой владеет правилом. Плоская папка `src` с 50 TypeScript-файлами затрудняет поиск границы функциональности.

### A3 · P2 · Проверять внутренние границы приложения

[check-boundaries.mjs](../../scripts/check-boundaries.mjs), функция `check` на строке 9, проверяет публичные exports Framework и выход относительных импортов за репозиторий. Он не задаёт правила направлений зависимостей между editor, ai, ai-server и слоями самого редактора.

Текущий результат проверки корректен в пределах её правил. Однако случайный импорт UI в пакет генерации или обход публичного входа другого workspace этой проверкой не предотвращается автоматически. Добавить явную матрицу разрешённых импортов и проверку циклов. Модель/команды должны обходиться без DOM и IndexedDB; UI связывается с хранилищем через явно переданные операции.

### A4 · P2 · Разделить хранилище, материалы и переносимый формат

[storage.ts](../../apps/editor/src/storage.ts) содержит создание БД и миграции, репозитории проектов, историю, asset hashing, нормализацию изображений, кэш, ИИ-черновик, импорт/экспорт проекта и очистку. Есть зависимость на `framework-adapter` для подготовки изображений.

Предлагаемое разделение: `db` и миграции; операции проектов/истории; репозиторий материалов; преобразование переносимого файла; операции черновика. Атомарные операции над несколькими stores должны сохранить общий координатор транзакции. Разносить такие записи по независимым транзакциям нельзя.

### A5 · P2 · Упорядочить CSS-слои

[app.ts](../../apps/editor/src/app.ts) импортирует последовательность общих и специализированных стилей; [ui.ts](../../apps/editor/src/ui.ts) дополнительно импортирует layout/styles. Повторные правила для header, canvas и controls распределены по `style.css`, `product.css`, `workspace.css`. В этих трёх файлах найдено 31 объявление `!important`.

Нынешняя проверка стилей полезна: она защищает токены и визуальные примитивы Framework. Но она не контролирует повторные определения и зависимость поведения от порядка подключения. Нужен один документированный вход стилей и разделение владельцев: shell, canvas, inspector, dialogs, responsive. После консолидации запускать существующие layout/keyboard/spacing-тесты. По этому аудиту текущая вёрстка работоспособна; речь о риске дальнейших регрессий.

### A6 · P2 · Исправить классификацию ошибок HTTP

Подтверждённый дефект [ai-server.ts](../../apps/ai-server/src/ai-server.ts): `JSON.parse(body)` на строке 45 падает в общий catch на строке 68.

Воспроизведение: `POST /api/ai/generate`, `Content-Type: application/json`, тело `{` → **503** с текстом `SyntaxError`. Валидный JSON `{}` → **400**.

Некорректное тело запроса должно давать 400 с понятным сообщением. Ошибки клиента, недоступность Ollama, таймаут и внутренняя ошибка должны иметь отдельные ветки. Выделить разбор тела и маршруты из общей функции HTTP-обработчика. Это также упростит проверку методов и единообразие ответов.

### A7 · P2 · Синхронизировать документацию с реальными версиями

- [docs/ru/architecture.md](../ru/architecture.md), строки 3 и 23: Framework 1.2.0 и схема 3.
- Английская архитектура повторяет версию 1.2.0.
- [README.en.md](../../README.en.md), строка 7: IndexedDB 2, схемы 1–3.
- В действительности зависимости фиксируют Framework **1.3.1**, код открывает IndexedDB **3**, а [project-import.test.ts](../../tests/project-import.test.ts) проверяет схемы **4 и 5**, включая slide annotations.

Зелёный `check:docs` проверяет наличие тем, переключателя языка и файлов ссылок, но не смысловую актуальность этих утверждений. Вынести факты о версиях в единый источник или генерируемый блок; явно различать версию БД, схему документа и версию переносимого файла проекта.

### A8 · P2 · Сделать воспроизводимость запуска и состояние сервисов явными

Базовый [compose.yaml](../../compose.yaml) содержит ссылки на образы, а сборка добавляется отдельным файлом. `VCS_REF` по умолчанию равен `local`; после обычной локальной сборки по metadata нельзя однозначно установить commit. API health не проверяет Ollama — это допустимое разделение liveness/readiness, но его нужно явно показывать оператору.

Нужны короткие команды для двух установок: editor без ИИ и полный продукт с моделью/документацией; build metadata с SHA; единая команда диагностики, перечисляющая состояние web, API, Ollama и документации. Сохранить возможность работать без ИИ. Не запускать второй Ollama поверх уже выбранного native runtime автоматически.

### A9 · P2 · Замерить стоимость редактирования больших документов

[model.ts](../../apps/editor/src/model.ts) клонирует и валидирует документ целиком; `inlineCommit` в `main.ts` получает несколько копий документа, сериализует его и ставит полный снимок на сохранение. `saveProject` снова валидирует и обходит изображения. `listAssets` читает все assets и settings, включая потенциально объёмный черновик.

На небольшом документе задержки не выявлены. Это **риск масштабирования, не подтверждённая проблема быстродействия**. Перед оптимизацией измерить время ввода, p95 сохранения, объём клонирования и открытие библиотеки на согласованных больших фикстурах. После измерений рассматривать получение одного immutable snapshot на изменение, чтение метаданных материалов отдельно от payload и перенос тяжёлого импорта из главного потока.

## UX и дизайн: что изменить

### U1 · P1 · Устранить два разных «заголовка» слайда

Шаги **14–16**, особенно [скриншот 16](../../artifacts/audit-2026-11-13/16-slide-title.png).

На первом слайде образца есть крупный текст «Из идеи — в результат». В свойствах поле «Заголовок слайда» пустое. Ввод «Проверка заголовка» добавляет второй крупный заголовок, а исходный остаётся. После проверки изменение отменено.

Причина: поле в `design.ts:88` изменяет `page.title`, а видимый заголовок композиции находится в текстовом widget. Пользователь не видит этого различия.

Нужно одно понятное действие «Изменить основной заголовок». Если оба вида заголовков нужны, обозначить назначение дополнительного и показать связь полей с элементами холста. Проверить такой же сценарий на остальных композициях, а также undo и экспорт.

### U2 · P2 · Сократить и объяснить настройки

Шаги **7, 10, 15**.

Редактирование простого текста открывает длинную панель: содержание, фрагменты, буквица, фирменное оформление, поверхность, порядок на устройствах, движение, геометрия. На телефоне даже базовые настройки секции занимают отдельный длинный экран. В настройках слайда рядом стоят «Подобрать оформление», «Оформить презентацию», «Изменить компоновку», «Выбрать композицию визуально».

Содержание и наиболее частые параметры оставить первыми; дополнительные группы раскрывать по задаче. Обозначить область действия: «Этот слайд» / «Все слайды». Развести понятия шаблона, компоновки и оформления через понятные подписи и превью. Слово «Воздух» заменить на более точное «Расстояния между элементами» либо дать пояснение. Сохранить доступ к текущим расширенным возможностям.

### U3 · P2 · Сделать завершение ИИ-сценария заметным

Шаги **11–12**.

В пустом состоянии значительная часть окна занята незаполненным результатом, а форма узкая. После генерации блок применения находится ниже видимой области; рядом остаются «Создать черновик», «Продолжить», «Повторить секцию». На скриншоте 12 есть техническая подпись **«Свойства: text»**.

Закрепить компактную область «Проверить → Применить» в пределах панели результата, сохранив доступность при увеличении текста и на телефоне. Показывать причину недоступности применения рядом с кнопкой. Оставлять «Продолжить» для действительно незавершённого черновика. Использовать локализованное название widget из registry вместо `w.type` в `panel.ts:84`.

### U4 · P2 · Объединить модель первого запуска

Шаги **1–4**; дополнительно проверен переход с `/` на сайт Framework docs.

Демо подписано Framework, проекты — Constructor, корень origin открывает отдельную документацию. На демо кнопки «Собрать из шаблона» и «Настроить элементы» создают один и тот же образец, но открывают разные места. Галерея без проектов сразу показывает поиск, сортировку, две крупные пустые категории; создание презентации оказывается ниже первого экрана 1440×1000. В диалоге по умолчанию выбран пустой проект.

Нужен согласованный вход в продукт и ясное различие «Открыть редактор», «Посмотреть образец», «Справочник Framework». Для пустой галереи показать компактный выбор формата и способа старта; поиск и сортировку сделать вторичными. Начало с образца — гипотеза для проверки с новичками, а не доказанная универсальная замена пустому холсту. Старые URL документации требуют совместимой миграции, если маршрут `/` будет изменён.

### U5 · P3 · Сделать библиотеку блоков информативнее

Шаг **5**.

Все девять карточек имеют одинаковое описание «Добавить в секцию». Текст и изображение находятся после кнопки, цитаты, карточек и галереи. Каталог занимает большую часть экрана, но почти не показывает различия результата.

Поставить основные типы первыми или сгруппировать их, заменить одинаковую строку коротким описанием назначения, добавить небольшие реальные превью. Для девяти типов отдельный поиск пока не обязателен.

### U6 · P2 · Сделать резервную копию понятной частью работы

Шаги **2, 6–8, 13**; [app.ts](../../apps/editor/src/app.ts), [storage.ts](../../apps/editor/src/storage.ts).

Интерфейс сообщает «Сохранено в браузере» и объясняет локальное хранение в помощи. Однако заметная команда — «Скачать HTML»; переносимый редактируемый JSON находится в меню проекта. Пользователь может принять HTML или Docker volume за резервную копию редактируемого проекта.

Назвать действие «Скачать редактируемый проект (.json)» / «Резервная копия» и сделать его доступным рядом с экспортом. В первом успешном сохранении кратко объяснить, где лежат проекты и как переносить их между браузерами. Не показывать постоянный тревожный баннер и не вводить навязчивое подтверждение каждого выхода. Смена `127.0.0.1` на `localhost`, порта или браузера означает другое хранилище — серверные контейнеры это не компенсируют.

## Направление организации файлов

Предлагаемая структура — ориентир для постепенных выделений, а не отдельная задача массового перемещения файлов:

```text
apps/editor/src/
  app/                 bootstrap, router, shell
  features/
    projects/          gallery, create, trash, preview
    editor/            session, canvas, outline, controls
    inspector/         properties, design, layout
    ai/                form, draft preview, review, apply
  domain/              editor model, document commands
  infrastructure/
    storage/           db, migrations, repositories, transaction coordinator
    assets/            normalization, cache, material loading
    project-file/      portable format, import/export
  shared/              UI helpers, focus, Framework adapter
```

Внешние `packages/ai` и `apps/ai-server` сохраняют свою роль. Модель и команды не импортируют браузерный UI или IndexedDB; `app` собирает зависимости. В tests полезно явно различать unit, browser/e2e и Framework contracts. Уже существующие `tests/framework/*` — преимущественно совместимые re-export-обёртки, а не скопированные исходники библиотеки; удалять их как дубли без проверки не следует.

## Очерёдность работ

| Этап | Изменения | Критерий готовности |
| --- | --- | --- |

## Границы вывода

Это инженерный и экспертный UX-разбор, а не исследование поведения реальных пользователей. Проверен выбранный набор Chromium-тестов, а не весь browser suite. Firefox, WebKit, реальные мобильные устройства, экранный диктор, печать/PDF и длительная работа с крупными библиотеками в этом запуске не проверялись. Нулевой результат axe не подтверждает полное соответствие WCAG.

Проведена одна успешная живая генерация секции; качество генерации по широкому набору тем и восстановление после всех возможных сбоев модели этим не подтверждаются. Для проверки offline использован документ без внешних HTTP-изображений; внешние материалы по-прежнему могут требовать сеть, о чём приложение предупреждает.

Исходный код приложения не перерабатывался в рамках аудита. Добавлен этот отчёт и локальные доказательства; последние находятся в игнорируемой Git папке `artifacts/audit-2026-11-13` и должны передаваться вместе с отчётом, если он нужен на другой машине.
